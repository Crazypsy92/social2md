试验遵循 `Crazypsy92/unified-content-notes`，读取版本为 `4fc18fcda056413a0e823c557045b95a636fc683`。没有人工听音参考文本，因此不计算 CER，也不把语义顺畅或多模型一致称为音频核验。样本目前都是 `REVIEW_REQUIRED`，适合作为复核稿，不应视为最终纠错定稿。

## 保真与格式检查

- 三份 `raw/` 备份与归档来源逐字节相同，SHA-256 与 `processed_items.json` 中的来源哈希一致。
- 原归档没有发生改动；校订稿只添加候选标记及一处有文字证据、但未核听的词形修改，没有删除原文字符。
- 三篇均保留来源链接和作者信息；机器清单以 `(platform, content_id)` 去重，文件按作者和标题命名。
- 三篇 Obsidian 笔记都通过 Unified Content Notes 所附 Callout 静态检查器。静态检查不等于 Obsidian 应用内渲染验收。
- 每篇均有独立校订稿、原文副本、候选 JSON、差异 JSON 和 Obsidian 笔记；正文保留完整转录，摘要明确区分讲者观点与独立事实核验。
- `py_compile` 通过；项目单元测试 41 项通过、1 项跳过（环境未安装 faster-whisper，跳过的为已安装音频解码器兼容性检查）。

## 归档差异说明

旧版 `docs/asr01_problem_analysis.md` 记载 ASR-01 第 2 篇曾有 2 个 U+FFFD，定位到旧运行目录中的 `output/bilibili_archive/BV1tqsF65Eks.md`。本次仓库内对应归档 `硬件何工/得电源者，得硬件.md` 检测到 0 个 U+FFFD。旧运行文件当前不在工作区可核对，故将其作为历史报告与当前归档版本之间的差异记录，不把“2 个乱码”计入本轮样本问题数。

## 可复用队列与调度

扫描器本轮检查了 91 篇归档，只生成候选和 SHA-256 进度，不改写其余文章。常规计划每轮上限为 3 篇；口播字符数达到 10,000 的文章单独列队。重复运行会按来源哈希跳过已有结果，变化的源文件进入 `SOURCE_CHANGED`，锁冲突或处理失败不会删除材料。发布命令只允许 `main`、只暂存 `docs/content_pipeline/`，并在推送前比较 `HEAD` 与 `origin/main`。

云端交互 shell 可能暂停，不适合作为常驻定时器。本轮已手动完成扫描、计划和三篇样本加工，但没有创建定时任务。若仓库设置允许 GitHub Actions 定时任务，可在确认私有仓库计划任务权限和额度后，用 `schedule` 加 `workflow_dispatch` 运行扫描/计划，设置 `concurrency` 并只给必要的 `contents` 写权限；未经人工维护的笔记摘要仍不会自动生成或发布。
